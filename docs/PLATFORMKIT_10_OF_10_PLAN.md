This program turns PlatformKit from a collection of strong libraries and
modules into a verifiably composable SaaS construction system.

“10/10” is not a subjective design score. It means every invariant below is
machine-verifiable from a clean checkout, without relying on the workspace
`go.work` file to hide dependency or release drift.

## Product invariant

A PlatformKit product selects capabilities. The composition engine resolves
their dependency closure. Each selected module contributes explicit runtime
bindings, UI intent, routes, permissions, events, migrations, tests, and
operational metadata. Deployment topology changes transport and placement,
not the business application being deployed.

## Non-negotiable architecture rules

1. A module is inert at import time. Production modules must not register
   migrations, seeds, tokens, assets, routes, or providers from `init()`.
2. A module has one authored descriptor. All other composition surfaces are
   generated projections.
3. There is one supported module materialization path.
4. Product composition is independent of deployment topology.
5. Backend core packages do not import frontend implementation packages.
6. A supported or core-certified maturity label is earned by executable
   evidence, not by catalog declaration alone.
7. Release verification runs with repository-local dependency metadata and
   `GOWORK=off`.

## Delivery sequence

### Phase 0 — Establish a trustworthy floor

Exit criteria:

- `platformkit-ports` API compatibility passes against its published baseline.
- `platformkit-backend-kit` runtime capability and release policy checks pass.
- `platformkit-apps` monolith and microservice modules build with `GOWORK=off`.
- Product and federated verification pass without stale selectors or missing
  module sums.
- CI contains a clean-checkout job that cannot inherit a developer workspace.

No release or later-phase completion claim is accepted while these gates are
red. Isolated migration slices may proceed only with executable proof and an
exact debt ratchet.

### Phase 1 — Converge module authoring

Exit criteria:

- `platform.ModuleDescriptor` is the only production module description.
- `platformfx` is the only supported materializer.
- The legacy standard composer has no production consumers.
- Module selection constructs isolated instances without import-time mutation.
- A compatibility adapter, if temporarily necessary, has a removal deadline and
  is forbidden for new modules.

Migration order:

1. one low-dependency supported module;
2. one core-certified module with migrations, events, and UI intent;
3. remaining modules in dependency-topological order;
4. delete the legacy path.

### Phase 2 — Generate composition surfaces

Exit criteria:

- The hand-maintained module registry is deleted.
- Module IDs, dependencies, maturity, permissions, events, migrations, and
  surface declarations are authored once.
- Catalogs, module sets, docs, manifests, and client projections are generated.
- CI regenerates into a temporary directory and fails on any diff.
- Generator output is deterministic across repeated runs.

### Phase 3 — Unify product composition

Exit criteria:

- One deployment-neutral product plan selects modules and capabilities.
- Monolith and microservice bootstraps consume the same resolved plan.
- Deployment adapters decide in-process versus remote bindings.
- A parity contract compares modules, routes, permissions, events, migrations,
  and public capabilities for every supported deployment shape.

### Phase 4 — Repair dependency direction

Exit criteria:

- Backend kernel packages no longer import the design system or frontend kit.
- Error rendering, HTMX, and browser-specific concerns live in web/application
  adapters.
- Dependency tests reject future backend-to-frontend implementation imports.
- The documented dependency graph matches `go list -deps` evidence.

### Phase 5 — Make certification honest

Exit criteria:

- Experimental is the default maturity for a new module.
- Supported modules meet statement and branch coverage floors and prove at
  least one vertical capability flow.
- Core-certified modules meet stricter coverage, compatibility, security,
  tenancy, failure-mode, migration, and observability gates.
- E2E flows reference reusable actions/components where applicable.
- Catalog maturity is generated from evidence; it cannot be raised by changing
  a string alone.

### Phase 6 — Operational closure

Exit criteria:

- Deployment manifests are generated from the same product/module plan.
- Health, readiness, migration ownership, event compatibility, telemetry, and
  rollback behavior are tested for both deployment shapes.
- A release candidate can be assembled, deployed, smoke-tested, and rolled back
  through one reproducible pipeline.

## Required proof on every phase

Each phase must ship with:

- a failing contract test that demonstrates the old defect;
- the implementation change;
- a passing clean-checkout verification;
- deletion of the superseded path;
- updated machine-readable architecture evidence;
- no unexplained allowlist or permanent waiver.

## Completion definition

The program is complete only when a new SaaS product can be defined by a small
product plan, assembled in either deployment shape, and proven by the same
contracts without editing a central registry or importing concrete modules into
the composition root.
